How GNOS flows

One page. Simple words. Read top to bottom in five minutes.

GNOS is a teaching plugin. A learner asks something. The machine reads the request, makes a plan, saves the learner's progress, teaches, adapts, and shows a web page. Files hold the plan. Small scripts check the files, save them safely, and build the page.

The flow, step by step

1

Ask

The learner writes anything. "Why divide by x here?" or "Teach me probability for finance over six weeks."

↓
2

Route

The orchestrator skill reads the request and picks: short answer, one lesson, or a full course. Small doubt? Answer now, no files. Big goal? Build a course.

↓
3

Research

For a course, the machine searches books and course sites. It writes down what it opened: definitions, order of topics, exercise ideas. Output: course-research.json.

↓
4

Plan

The machine writes course.json: title, goal, chapters, topics, sources, one current topic. Each topic lists its representations — which part needs animation, image, simulation, or text. A checker script validates the shape.

↓
5

Enroll

Name known? Use it. Not known? Save as learner and say so in one line. The plan is copied into the learner's folder. No "learner ID" talk.

↓
6

Ask to show

Same turn, the machine asks: "want to see the course now?" On yes, it renders the page and returns the link. A course turn never ends without rendering or asking.

↓
7

Teach and track

Teaching happens in chat. Every try, repeat, and stuck point is saved in the learner record. 1 repeat = rephrase. 2 = add a step. 3 = split or swap the source.

↓
8

Make media

Each topic part goes to its skill: motion → Manim video, structure → image model, interaction → small HTML simulation, handout → PDF. Every file is registered in the manifest.

↓
9

Show

The viewer script rebuilds one static page: sidebar, lessons, videos, images, simulations, exercises, sources. Chips flip from planned to ready as files arrive.

Two files never mix: course.json holds the route (what is next). state.json holds the evidence (what was hard). The route changes only when the evidence says so.

Worked example — probability course

A learner asks for probability for finance over six weeks. Watch the files change:

1. research  →  course-research.json   (MIT 18.05 opened, chain order checked)
2. plan      →  course.json            (title, goal, 5 chapters, current = probability-models)
3. check     →  validate_course.py     ("Valid: ... (12 topics)")
4. enroll    →  learners/learner/courses/probability-.../course.json
5. ask       →  "want to see the course now?"  →  yes
6. render    →  portal/index.html      (contents + sources + plan chips, zero lessons yet)
7. teach     →  chat + state.json      (try saved, repeat counted)
8. stuck x2  →  revision 2            ("added composition bridge after 2 repeats")
9. manim     →  artifacts/videos/...   (registered ready → chip flips ready)
10. re-render →  portal/index.html      (video inline in the lesson)
If the page is missing, check in order: was the plan enrolled? (learners/<name>/courses/<id>/course.json must exist) — was it rendered? (portal/index.html must exist) — only then start the server. Never render from a blueprint outputs/ file.
